SECTION 1 — PROJECT IDENTITY
================================================================================

Project name        : PortfolioIQ (repo header calls it "Portfolio Insights AI")
Full project title  : PortfolioIQ — AI-Powered Stock Portfolio Risk &
                      Diversification Analyzer (with local RAG intelligence)
Purpose             : Manage stock portfolios with REAL market data, measure where
                      risk actually comes from, explain it in plain language, map
                      news/events to your own holdings, and provide evidence-based
                      BUY/HOLD/AVOID decision support — never predictions.
Problem statement   : Retail investors see prices and P&L but not WHY a portfolio
                      is risky, how news affects THEIR holdings, or whether a
                      stock fits THEIR portfolio. Generic trackers stop at value +
                      allocation; research tools stop at generic analysis.
Main objectives     :
  1. Real, provenance-stamped market data (no fabricated numbers).
  2. Covariance-based quantitative risk with exact contribution decomposition.
  3. News → entity → event → portfolio-exposure → alert intelligence pipeline.
  4. Local, ₹0-cost AI: RAG over the user's own data + a quantized local LLM
     that EXPLAINS but never calculates authoritative numbers.
  5. Transparent BUY/HOLD/AVOID from a deterministic decision engine.
  6. Full-stack database-systems rigor: 19 tables, FKs, CHECKs, triggers,
     functions, a stored procedure, a view, audit logging.
Target users        : Students/developers (academic DB project + resume project),
                      DIY Indian-market investors (NSE symbols, ₹, NIFTY benchmark).
Differentiators vs a basic tracker:
  - Risk attribution (Euler decomposition), not just allocation percentages.
  - Benchmark-relative analytics (Beta/Alpha vs NIFTY 50) with honest N/A states.
  - Transaction-true P&L (realized vs unrealized) reconstructed from history.
  - Event intelligence mapped to YOUR exposure with deterministic importance.
  - Grounded local AI: retrieval-gated, citation-forced, cache-versioned;
    the LLM NEVER invents prices/metrics and NEVER decides alone.
  - Missing data is shown as N/A with a reason — never converted to 0.

High-level workflow (complete):
  Register/Login → create portfolio → add holdings (or import) → record BUY/SELL
  transactions → Yahoo sync fills stock_prices/benchmark_prices (45-min scheduler)
  → GDELT fetches news → entity matching → events → portfolio impact rows →
  deterministic importance → alerts (dedup+cooldown) → user opens Dashboard/Risk/
  Intelligence/Stock Detail → quantitative engines compute from stored prices →
  RAG indexes documents → user asks AI question / runs AI Deep Analysis →
  retrieval → grounding gate → Qwen3-4B → cited, structured explanation →
  deterministic decision engine → BUY/HOLD/AVOID + LLM narrative.

Explaining the project:
(1) ONE SENTENCE
    PortfolioIQ is a full-stack PostgreSQL-centric portfolio intelligence platform
    that combines real Yahoo market data, deterministic quantitative risk
    analytics, news-event intelligence, and a locally-hosted grounded RAG+LLM
    stack to explain risk and support BUY/HOLD/AVOID decisions without ever
    predicting prices or fabricating data.

(2) 30-SECOND EXPLANATION
    "PortfolioIQ manages stock portfolios backed by real market data, computes
    covariance-based risk with exact per-holding risk contributions, compares
    against NIFTY, reconstructs true P&L from transactions, and turns news into
    events that are mapped to your actual exposure and alerts. A local RAG stack
    (FAISS + Qwen3-Embedding) retrieves evidence and a quantized Qwen3-4B model
    running through Ollama explains the numbers — it never calculates them. The
    BUY/HOLD/AVOID recommendation comes from a transparent deterministic scoring
    engine; the LLM only narrates it."

(3) 2-MINUTE EXPLANATION
    Add the 30-second version, then: "The database is the source of truth — 19
    tables with FKs, CHECKs, unique business keys, triggers, a view, three
    functions and one stored procedure. Yahoo Finance data is synced every 45
    minutes with per-row provenance; Alpha Vantage is an optional fallback.
    News comes from GDELT (Marketaux optional), is normalized, matched to
    stocks via a confidence-tiered matcher, and consolidated into events with a
    lifecycle. Each event is scored deterministically (severity 0.30,
    directness 0.20, relevance 0.15, sources 0.15, recency 0.10, category 0.10)
    and only HIGH/CRITICAL events trigger AI analysis. Risk math is exact:
    portfolio volatility = sqrt(wᵀΣw), contributions via Euler decomposition,
    historical VaR/CVaR from date-aligned returns. The AI layer embeds curated
    documents into FAISS (1024-dim Qwen3-Embedding-0.6B), retrieves with a
    minimum-score gate, and only then calls Qwen3-4B (q4_K_M, ~4.5 GB VRAM)
    which must cite [E1]…[En] evidence and output Zod-validated JSON. The
    decision engine scores six factors and applies documented bands: BUY ≥ 62
    with confidence ≥ 45% and risk ≠ VERY_HIGH; AVOID ≤ 42; else HOLD; evidence
    quality < 0.30 → INSUFFICIENT_EVIDENCE."

(4) 5-MINUTE TECHNICAL EXPLANATION
    Everything above, plus:
    - Request path: React (TanStack Start, SSR) → fetch /api → Vite proxy in
      dev → Express 5 middleware chain (helmet, cors, morgan, JSON body limit,
      requireAuth JWT, Zod validate, rate limiter) → controller → service →
      Prisma → PostgreSQL. Central error handler maps errors to safe JSON;
      HttpError carries status/code; no stack traces in production.
    - Auth: bcryptjs hashing (10 rounds default), JWT (7d default) with
      issued-at vs users.password_changed_at invalidation, roles USER/ADMIN,
      ownership checks in services (403 on non-owner, 404 to avoid leaking).
    - Market sync: startup run after 8 s, then setInterval 45 min
      (MARKET_DATA_REFRESH_MINUTES); per-provider MarketDataResult (failure is
      data, not exceptions); sanity validation (high ≥ low, prices > 0,
      OHLC consistency); upserts with data_source provenance; every run logged
      in market_data_syncs.
    - Intelligence: ingest every 30 min (min 15) + cleanup every 60 min;
      raw articles TTL 72 h; events consolidated by deterministic rules; alerts
      one-per-event-per-user with 24 h cooldown; watchlist/sector exposure can
      never inflate intrinsic severity past MEDIUM.
    - AI: five document types (NEWS, EVENT, STOCK_INFORMATION,
      FINANCIAL_INFORMATION, HISTORICAL_EVENT) built deterministically from
      tables; FAISS IndexFlatIP (inner product = cosine on normalized vectors);
      admin rebuild or incremental append after ingest; retrieval top-K 6,
      min score 0.35, evidence budget 6000 chars; research flow runs SIX
      targeted queries, merges, dedupes, reranks. LLM runs at temperature 0.2,
      max 512 tokens, 90 s timeout; outputs parsed with fenced-JSON tolerance
      and validated by Zod.
    - Testing: 68 deterministic node:test tests (28 AI/RAG, 25 providers/
      intelligence, 15 research) + live API/RBAC/DB-integrity verification.

SECTION 3 — COMPLETE SYSTEM ARCHITECTURE

MAIN REQUEST PATH (every arrow explained):
  USER (browser)
    ↓  user interacts with React pages (src/routes/_app.*.tsx)
  REACT FRONTEND (React 19 + TanStack Start SSR)
    ↓  services in src/services/*.service.ts call fetch() via api-client.ts
       (API_BASE_URL = VITE_API_BASE_URL ?? "/api"); TanStack Query caches and
       re-fetches; JWT stored client-side and sent as Authorization: Bearer.
  REST API (/api/...)
    ↓  Vite dev proxy (or same-origin in prod) forwards to Express
  EXPRESS APP (backend/src/app.ts)
    ↓  middleware order: helmet → cors(allow-list) → morgan → express.json
       {limit:"1mb"} → routers; each router chain adds requireAuth / RBAC /
       rate-limit / validate(schema)
  MIDDLEWARE (auth.ts, validate.ts, rate-limit.ts, error.ts)
    ↓  validate.ts parses with Zod → 400 VALIDATION_ERROR on failure;
       requireAuth verifies JWT and loads the user; error.ts centralizes
  CONTROLLER (backend/src/controllers/*.controller.ts) — THIN: extracts
    authenticated user + validated input, calls one service, wraps ok(res,data)
    ↓
  SERVICE (backend/src/services/**) — ALL business logic + ownership checks +
    audit writes live here; controllers contain no queries
    ↓
  PRISMA ORM (utils/prisma.ts singleton)
    ↓  parameterized SQL; raw SQL only via $queryRawUnsafe/$executeRawUnsafe
       with bound $n parameters (e.g. the stored-procedure CALL)
  POSTGRESQL (19 tables + view + functions + 1 procedure)

MARKET DATA PATH (arrows explained):
  YAHOO FINANCE / ALPHA VANTAGE  [EXTERNAL API]
    ↓  each provider adapter (market-providers/yahoo.provider.ts,
       alphavantage.provider.ts) returns MarketDataResult<T> — SUCCESS shape
       {ok:true, data, provenance:{provider,fetchedAt,…}} or
       {ok:false, error:{code,message}}. Failure is DATA, never a throw.
  MARKET PROVIDER REGISTRY (market-providers/registry.ts)
    ↓  ordered chain; registry returns enabled providers (Yahoo always;
       Alpha Vantage only if key configured); fallback.ts walks the chain:
       try provider 1 → if !ok and next exists → try provider 2 → else
       record failure. A quota/rate-limit result is NOT retried blindly.
  SYNC ENGINE (market-data.sync.ts)
    ↓  sanity validation (price>0, high≥low, open/close within range, date not
       future, symbol mapping exists) → invalid rows are SKIPPED (never
       invented); valid rows are UPSERTED with data_source provenance;
       fundamentals update stocks table columns; per-run stats written to
       market_data_syncs; per-stock failure isolated (one bad symbol never
       stops the run).
  POSTGRESQL (stock_prices, stocks, benchmarks, benchmark_prices,
  market_data_syncs)

NEWS/INTELLIGENCE PATH (arrows explained):
  NEWS PROVIDERS (GDELT [no key] / Marketaux [OPTIONAL key])
    ↓  providers normalize to a common NormalizedArticle shape; per-provider
       failure isolated; news-registry.ts aggregates all configured providers
  NEWS REGISTRY + INGEST (news-registry.ts, news-ingest.ts)
    ↓  article-level dedup via UNIQUE(provider, provider_article_id);
       cross-provider duplicates converge later at EVENT level (same event,
       multiple evidence rows retained — never deleted)
  ENTITY MATCHING (news/entity-matcher.ts)
    ↓  hierarchy: provider symbol → exact company/alias name → symbol text →
       sector/context. Each match stores match_confidence tier
       (VERY_HIGH/HIGH/MEDIUM/LOW) in intelligence_news_entities; weak matches
       are stored but flagged LOW (never claimed as direct).
  EVENT ENGINE (event-categoriser, event-impact, event-lifecycle services)
    ↓  rule-based categorization (COMPANY/GOVERNMENT/POLICY/TAX/SUBSIDY/
       REGULATION/MACRO/COMMODITY/GEOPOLITICAL/SECTOR/EARNINGS/CORPORATE_ACTION/
       OTHER); same-event articles consolidate into one event (article_count,
       source_names accumulate); lifecycle NEW→UPDATED→PROCESSED→RESOLVED/
       EXPIRED (+ARCHIVED/DISMISSED valid states)
  PORTFOLIO EXPOSURE (portfolio-exposure.service.ts)
    ↓  per user: DIRECT_HOLDING (owns stock) / WATCHLIST / SECTOR_EXPOSURE /
       INDIRECT / MACRO / COMPETITOR / SUPPLIER / CUSTOMER exposure rows in
       intelligence_portfolio_impacts with portfolio_weight, sector_weight,
       user_aggregate_weight computed from holdings × latest close [BACKEND CALC]
  IMPORTANCE + ALERTS (event-importance.service.ts, alert-priority.service.ts,
       alert-delivery.service.ts)
    ↓  deterministic scoring (Section 14) → priority blending → ONE alert per
       event per user, 24 h cooldown, watchlist/sector rows capped at MEDIUM;
       rows inserted into alerts (source='INTELLIGENCE', links to event/impact)
  ALERTS TABLE → user UI (Alerts page, Dashboard feed)

AI / RAG PATH (arrows explained):
  USER QUESTION or EVENT/RESEARCH TRIGGER
    ↓  POST /api/ai/query or /api/ai/stock/:symbol/analyze or
       /api/ai/event/:id/analyze (rate-limited 10/min)
  AI SERVICE (ai/service.ts / ai/research/stock-research.service.ts)
    ↓  resolves stock FIRST from DB (AI-independent; unknown symbol → 404);
       checks AI availability (Ollama probe) — if down → structured
       UNAVAILABLE response with reason; NO fabrication
  RETRIEVAL (ai/retriever.ts; research-retrieval.service.ts for deep analysis)
    ↓  builds query text; research flow runs SIX targeted queries (company
       news, company events, sector events, macro/policy, historical analogues,
       financial info)
  EMBEDDING MODEL (ai/embedding.ts → Qwen3-Embedding-0.6B via Ollama /api/embed)
    ↓  query text → 1024-dim vector [EMBEDDING]
  FAISS (ai/vector-store.ts, IndexFlatIP)
    ↓  cosine similarity (inner product on normalized vectors) → top-K=6
       candidates above minScore=0.35; metadata from documents.json gives
       provenance; research flow merges all queries, dedupes by documentId,
       reranks, trims to 6000-char evidence budget
  GROUNDING GATE (ai/grounding.ts)
    ↓  if zero/low-quality evidence → refuse: deterministic "insufficient
       evidence" response; LLM IS NOT CALLED
  PROMPT BUILDER (ai/prompts.ts, research-prompts.ts)
    ↓  layered prompt: system (evidence-grounded analyst) + financial-analyst
       rules (never calculate, never predict, cite [E#], separate facts from
       interpretation) + authoritative pre-computed numbers (labelled) +
       evidence block + user question
  QWEN3-4B via OLLAMA (ai/llm.ts, POST /api/chat, temperature 0.2,
       max 512 tokens, 90 s timeout) [AI/LLM]
    ↓  raw text → extractJsonBlock handles fenced JSON/trailing commas
  ZOD VALIDATION (ai/output-schema.ts / research/report-schema.ts)
    ↓  malformed LLM output → structured error, never a crash, never stored
  STRUCTURED RESPONSE (JSON with analysis, key_factors, evidence[], confidence)
    ↓  cached where applicable (research fingerprint cache; event ai_analysis
       JSONB) → FRONTEND renders with expandable citations

Cross-cutting: EVERY financial number shown anywhere is [DATABASE] or
[BACKEND CALC]. [AI/LLM] output appears ONLY inside clearly-labelled AI panels
(AI insights, event AI assessment, AI Deep Analysis report) and always carries
citations + the disclaimer. Providers supply DATA, not recommendations.

--- 4.1 users -------------------------------------------------------------------
Purpose: accounts + RBAC + password-invalidation anchor.
PK: user_id (serial). Written by: register (U), seed, admin (role update).
Read by: auth middleware (every request), all ownership queries, admin.
Columns:
  user_id            Int         PK, autoincrement
  name               VarChar(100) NOT NULL                         [U]
  email              VarChar(255) NOT NULL UNIQUE (case as provided) [U]
  password_hash      VarChar(255) NOT NULL (bcrypt, never returned by APIs)[U→hash]
  role               VarChar(20)  NOT NULL DEFAULT 'USER'; CHECK role IN
                     ('USER','ADMIN')                               [D/U]
  password_changed_at Timestamp(6) NULL — JWTs issued before this are
                     rejected (password-change invalidation)          [B]
  created_at/updated_at Timestamp(6) NOT NULL DEFAULT now(); updated_at
                     maintained by trigger trg_users_updated_at        [D/B]
FKs: referenced by portfolios, watchlists, alerts, audit_logs,
     intelligence_portfolio_impacts (all ON DELETE CASCADE except audit_logs
     which is ON UPDATE NoAction / SET NULL on user delete? — audit user_id is
     nullable with onUpdate: NoAction).
Example: (1, 'Demo User', 'user@portfolioiq.dev', '$2a$…', 'USER', NULL, …)

--- 4.2 stocks ------------------------------------------------------------------
Purpose: stock master universe (38 rows: NSE symbols like RELIANCE, TCS…).
PK: stock_id. UNIQUE(symbol, exchange). Indexes: idx_stocks_sector,
    idx_stocks_symbol.
Columns:
  stock_id Int PK; symbol VarChar(20) NOT NULL [A/seed]; company_name
  VarChar(150) NOT NULL [A]; sector VarChar(100) NOT NULL [A];
  industry VarChar(100) NULL; exchange VarChar(20) NOT NULL ('NSE') [A];
  description Text NULL; market_cap Decimal(20,2) NULL CHECK market_cap>=0
  [A=Yahoo quoteSummary]; pe_ratio Decimal(10,2) NULL [A];
  dividend_yield Decimal(8,4) NULL [A]; is_active Bool DEFAULT true [D];
  yahoo_symbol VarChar(30) NULL (provider symbol e.g. RELIANCE.NS) [A/D];
  data_source VarChar(20) DEFAULT 'DEMO' — provenance 'DEMO'|'YAHOO' [B];
  fundamentals_updated_at Timestamp NULL (freshness stamp) [B];
  created_at/updated_at (trigger trg_stocks_updated_at).
Writers: seed, market-data sync (fundamentals), admin.
Readers: stock explorer/detail, intelligence entity matching, analysis engines.

--- 4.3 stock_prices ------------------------------------------------------------
Purpose: daily OHLCV history; the substrate for EVERY calculation.
PK: price_id. UNIQUE(stock_id, price_date). FK stock_id → stocks
    ON DELETE CASCADE. CHECK: low<=high, open BETWEEN low AND high,
    close>0, volume NULL OR >=0.
Columns: stock_id [O]; price_date Date [A]; open_price/high_price/low_price/
close_price Decimal(18,2) [A]; volume BigInt NULL [A]; data_source
VarChar(20) DEFAULT 'DEMO' ('DEMO'|'YAHOO'|'ALPHA_VANTAGE' after the
provenance migration) [B=provenance stamp of provider used];
(no created_at column — uniqueness handles dedup).
Writers: market-data sync (S), seed. Readers: analytics/risk/benchmark/
research engines, charts, stored procedure.

--- 4.4 portfolios --------------------------------------------------------------
Purpose: user-owned portfolio containers.
PK: portfolio_id. FK user_id → users CASCADE. Index: implicit PK; updated_at
    trigger trg_portfolios_updated_at.
Columns: portfolio_id; user_id [auth context]; name VarChar(100) NOT NULL [U];
description Text NULL [U]; created_at/updated_at.
Writers: portfolios.routes POST/PUT/PATCH/DELETE (U). Readers: dashboard,
analysis, intelligence exposure, risk pages.

--- 4.5 holdings ----------------------------------------------------------------
Purpose: current position per (portfolio, stock).
PK: holding_id. UNIQUE(portfolio_id, stock_id). FKs: portfolio_id CASCADE,

================================================================================
SECTION 6 — DATABASE NORMALIZATION
================================================================================
1NF: every column atomic (no comma lists; repeating evidence stored as JSON
     ARRAYS/ids, not delimited strings), PK on every table.
2NF: no table has a composite business key except stock_prices
     (stock_id,price_date) / benchmark_prices / risk_snapshots /
     intelligence_news_articles (provider,provider_article_id) / holdings
     (portfolio_id,stock_id) / watchlists (user_id,stock_id) / stocks &
     benchmarks (symbol,exchange) — in every case ALL non-key attributes
     depend on the FULL key (e.g. a price row's OHLC depends on the exact
     stock+date; a holding's quantity depends on portfolio+stock).
3NF: no transitive dependencies — e.g. stock_prices stores no company_name;
     holdings stores no sector (joined via stocks); alerts store ids, not
     event text copies; sector lives ONLY in stocks.

Intentional, documented deviations (NOT hidden):
  - JSONB columns: raw_metadata, provider_metadata, source_article_ids,
    source_names, ai_analysis — semi-structured provider output / cached AI
    assessment. Justified: schema-flexible evidence, read as a whole.
  - Cached counters on intelligence_news_events: article_count,
    material_updates — recomputed during consolidation, avoid N+1 counts.
  - Provenance stamps (data_source on stocks/stock_prices/benchmark_prices/
    benchmarks, source on alerts) — deliberate provenance denormalization.
  - intelligence_portfolio_impacts stores computed weights (portfolio_weight,
    sector_weight) at impact time — a snapshot of exposure as valued THEN
    (price_as_of records freshness); it is derived data by design.
  - portfolio_analysis / portfolio_risk_snapshots are derived CACHE tables
    (documented as such) — historical snapshots, never recomputed.
  - v_portfolio_summary computes value on read (no stored value column).

LOGIN FLOW (exact):
LOGIN FORM (src/routes/login.tsx, react-hook-form + zod)
  → POST /api/auth/login  [USER INPUT]
  → authLimiter (rate-limit middleware, per-IP buckets)
  → validate(loginSchema): email format, password min length → else 400
  → auth.controller.login → auth.service.login
  → users.findUnique({email}) — not found → generic 401
     "Email or password is incorrect." (no user-enumeration hint)

     LOGIN_FAILED audited (no password logged)
  → jwt.sign({userId, role, iat}, JWT_SECRET, {expiresIn: JWT_EXPIRES_IN='7d'})
     [CONFIGURATION: JWT_SECRET from env; in non-production a dev fallback
     exists but production rejects placeholder-looking secrets < 40 chars]
  → response {data:{token, user:{…safe fields…}}} — password_hash NEVER
     serialized (explicit select lists)
CLIENT: token kept by auth.service; api-client attaches
  "Authorization: Bearer <token>" to every request.
AUTH MIDDLEWARE (middleware/auth.ts requireAuth)
  → verify JWT signature+expiry → load user row (role, password_changed_at)
  → if user.password_changed_at && token.issuedAtMs < password_changed_at
    → 401 (password-change invalidation)
  → req.user = {userId, role} → controllers read currentUser(req)
REGISTER: POST /api/auth/register → same validation; duplicate email →
  409 CONFLICT "already exists"; password hashed with bcrypt (BCRYPT_ROUNDS
  default 10); new user role USER (no self-admin).
LOGOUT: client discards token (server holds no session state; JWT is
  stateless). Server-side revocation NOT IMPLEMENTED beyond password-change
  invalidation.
Errors: 401 invalid/missing/expired token ("Your session has expired…"),
401 bad credentials, 429 rate-limited, 400 validation.
Secrets: JWT_SECRET, DATABASE_URL, provider keys — all env-only; backend/.env
is git-ignored; .env.example files contain placeholders only (verified by
repo-wide secret scan).

SECTION 14 — INTELLIGENCE ENGINE
================================================================================
PIPELINE (every stage):
News fetch (SCHEDULED 30 min / MANUAL) → article normalize + dedup →
entity extraction/matching → event detection/classification → consolidation
→ lifecycle → importance scoring → portfolio exposure → alert priority →
alert delivery.
1. ENTITY MATCHING (news/entity-matcher.ts) [DETERMINISTIC]
   Hierarchy: (1) provider-provided symbol/ticker → VERY_HIGH;
   (2) exact company_name/known alias → HIGH; (3) symbol text match →
   MEDIUM; (4) sector/context match → LOW (flagged; never claimed direct).
   Stored per article in intelligence_news_entities.match_confidence.
2. EVENT CLASSIFICATION (event-categoriser.ts) [DETERMINISTIC]
   Category from keyword/rule sets: COMPANY, GOVERNMENT, POLICY, TAX,
   SUBSIDY, REGULATION, MACRO, COMMODITY, GEOPOLITICAL, SECTOR, EARNINGS,
   CORPORATE_ACTION, OTHER. Severity 1..5 assigned by rule table; direction
   UP/DOWN/NEUTRAL where inferable.
3. CONSOLIDATION [DETERMINISTIC]: near-duplicate articles → ONE event;
   article_count and source_names (distinct sources) accumulate;
   material_updates++ when new evidence materially changes the event
   (status → UPDATED). Same event ≠ 3 alerts.
4. LIFECYCLE (event-lifecycle.service.ts): NEW → UPDATED → PROCESSED (impacts
   built) → RESOLVED / EXPIRED; ARCHIVED / DISMISSED remain valid states.
   EXPIRED events' alerts survive (SET NULL FK design).
5. IMPORTANCE SCORING (event-importance.service.ts) [DETERMINISTIC — exact
   implementation]:
   score ∈ [0,1] = Σ (signal × weight); every component returned for UI:
     severity    weight 0.30  (event severity 1..5 → 0.2..1.0)
     directness  weight 0.20  (DIRECT=1.0, SECTOR=0.5, MACRO=0.25)
     relevance   weight 0.15  (best entity-match confidence/relevance)
     sources     weight 0.15  (distinct sources: 1→0, 2→0.5, 3+→1)
     recency     weight 0.10  (linear decay over 48 h from detection)
     category    weight 0.10  (policy/tax/regulation/geo > earnings >
                              company > other)
   Thresholds: ≥0.85 DIRECT → CRITICAL; ≥0.70 HIGH; ≥0.50 MEDIUM; ≥0.40
   WATCH; else LOW (a single stale low-relevance mention is LOW, not WATCH).
   AI involvement in the score: NONE.
6. PORTFOLIO EXPOSURE (portfolio-exposure.service.ts) [BACKEND CALC]
   For every sufficiently relevant event × user: does the user own the stock?
   (DIRECT_HOLDING + portfolio_weight from holdings × latest close), is it
   watchlisted (WATCHLIST), sector match (SECTOR_EXPOSURE + sector_weight),
   indirect/macro (INDIRECT/MACRO_EXPOSURE), competitor/supplier/customer
   relations when modelled. Idempotent impact rows (functional unique).
7. ALERT PRIORITY (alert-priority.service.ts) [DETERMINISTIC]
   Blends intrinsic importance with exposure: watchlist/sector-only rows are
   CAPPED at MEDIUM (a watchlist item must never page the user like a
   holding); CRITICAL requires intrinsic CRITICAL importance AND direct
   holding exposure. Output: alert_candidate on the impact row.
8. ALERT DELIVERY (alert-delivery.service.ts): creates the alert row
   (source='INTELLIGENCE', links event+impact), ONE per event per user,
   cooldown NEWS_ALERT_COOLDOWN_HOURS (default 24 h), dedup against unread
   duplicates. POST /api/admin/intelligence/alerts/deliver forces a pass.

What is deterministic vs AI:
  EVERYTHING above is deterministic rule code. The ONLY AI is the cached
  natural-language assessment for HIGH/CRITICAL events
  (ai-event-analysis.service.ts), which reads the SAME numbers and must cite
  evidence; insufficient retrieval → no AI claim stored.

SECTION 16 — QUANTITATIVE FINANCE ENGINE
================================================================================
ALL metrics below are [BACKEND CALC] over [DATABASE] prices. THE LLM COMPUTES
NONE OF THEM. Files: services/news/quantitative-risk.service.ts (risk core),
services/analytics.service.ts (portfolio/stock metrics), services/
benchmark-performance.service.ts, services/transaction-performance.service.ts,
services/health-score.service.ts.
Global assumptions (visible in the UI): TRADING_DAYS=252; annualization
×√252 for volatility-type, ×252 for mean returns; risk-free default 6.5% p.a.
[CONFIGURATION via riskFreeRatePct input] ÷ 252 for daily; VaR confidence
default 95% [USER INPUT on the page]; returns are SIMPLE daily returns from
DATE-ALIGNED closes restricted to each series' latest homogeneous data-source
segment (latestHomogeneousSegment — no mixing DEMO/YAHOO/ALPHA_VANTAGE rows).

• Returns: r_t = P_t / P_{t−1} − 1 on aligned dates. Gap days excluded by
  alignment, never position-matched.
• Volatility (portfolio): σp = sqrt(wᵀΣw) × √252 × 100. w = current weights
  (value-based). Variance clamped ≥ 0; < 2 observations → N/A metric.
• Covariance matrix Σ: sample covariance (n−1 denominator) of aligned stock
  return columns (covarianceMatrix()). Correlation: cov/(σa·σb) — pairwise,
  reported with average + top pairs.
• Max drawdown: running-max path → dd_t = V_t/max(V) − 1 → min × 100.
  Recovery duration: trading days trough → first dd ≥ 0 (or last obs).
• Downside deviation: sqrt(Σ (r_t − target)² / N_total) over returns BELOW
  target (target default 0% daily), annualized ×√252.
• Sharpe = (mean_r − rf_daily)/σ_daily × √252. σ=0 → null.
• Sortino = (mean_r − rf_daily)/downsideDev_daily × √252.
• Calmar = annReturn / |maxDD|.
• VaR 95 / VaR 99 (HISTORICAL): empirical quantile of aligned daily portfolio
  returns at 0.05/0.01 (percentileSorted) × 100. Labelled "not a guaranteed
  maximum".
• CVaR (expected shortfall): mean of returns ≤ VaR-quantile (worst-5% mean).
• Beta (vs NIFTY): Cov(Rp,Rm)/Var(Rm) on date-aligned daily pairs
  (benchmark-performance.service); insufficient paired observations → N/A
  with reason. Data: benchmark_prices + stock_prices.
• Alpha (Jensen): Rp_ann − [rf + β(Rm_ann − rf)] with the SAME 6.5% rf
  [CONFIGURATION]; N/A when beta N/A.
• Tracking error: std of (Rp − Rm) paired differentials × √252.
• Information ratio: (annRp − annRm)/TE; TE=0 → null.
• Upside/downside capture: mean Rp on benchmark-up (down) days ÷ mean Rm on
  those days × 100.
• HHI = Σ w_i². Effective positions = 1/HHI. On current value weights.
• Diversification ratio = Σ(w_i × σ_i,standalone) / σp (> 1 = benefit).
• Risk contributions (EXACT Euler decomposition):
    marginal risk_i   = (Σw)_i / σp
    component risk_i  = w_i (Σw)_i / σp
    % contribution_i  = w_i (Σw)_i / (wᵀΣw) × 100   (sums to 100%)
  Ranking: ≥30% High, ≥15% Moderate, else Low. Behind "Why is my portfolio
  risky?".
• Portfolio value / P&L: value = Σ qty × latest close [DATABASE];
  unrealized = value − Σ qty × avg_buy_price; % = /cost. Dashboard and
  v_portfolio_summary agree (view uses fn_latest_close).
• Realized P&L: ledger reconstruction (transaction-performance.service):
  sells at price vs weighted-average cost of shares sold; unrealized = open
  positions at latest close; total = realized + unrealized. Version:
  transaction-attribution-v1.
• Turnover: buy/sell turnover over window (traded value ÷ mean portfolio
  value); transaction counts; average holding duration.
• Holding period: first purchase → today (or exit); annualized return only
  when meaningful.
• Risk score (0–100): documented legacy band = min(100, vol%×0.6 +
  |maxDD%|×1.6) — used in portfolio_analysis and the stored procedure.
  Diversification score = 100 × (1 − HHI).
• PortfolioIQ Health Score (health-score-v1) [DETERMINISTIC composite]:
  concentration 0.25 (1 − normalized HHI), risk-concentration 0.20 (1 − top
  contributor's excess above parity), diversification ratio 0.15 (soft cap
  2.0), drawdown 0.15 (1 − |maxDD|/50%), volatility 0.15 (0–60% band), event
  exposure 0.10 (1 − affected value share). Missing components dropped,
  weights re-normalized; N/A if nothing computable. Labelled a relative
  model output — not objective truth.
• Benchmark return / excess return: aligned-window cumulative comparisons.

NOT IMPLEMENTED metrics: Monte Carlo VaR, parametric VaR, options Greeks,
DCF, FIFO/LIFO tax lots (weighted average only), currency-hedging analytics.

SECTION 19 — TRANSACTION-BASED P&L
================================================================================
BUY: prisma.$transaction(async tx => …) — ATOMIC:
  1. findUnique holding (portfolio, stock).
  2. Exists → newQty = qty + q; newAvg = (qty×avg + q×price)/newQty
     (weighted average cost); tx.holdings.update.
     Not exists → tx.holdings.create {quantity: q, average_buy_price: price}.
  3. tx.transactions.create (ledger row; BUY/SELL CHECK-enforced).
SELL: same atomic block — qty reduced; realized P&L = (sell_price −
  weighted_avg_cost) × qty_sold (weighted average, NOT FIFO/LIFO — FIFO/LIFO
  NOT IMPLEMENTED); holding row deleted at qty 0 (ledger retained); oversell
  (qty > held) → 400.
Realized/unrealized/total (transaction-attribution-v1):
  reconstructPortfolio() walks the ledger chronologically to rebuild holdings
  at ANY date → historical value series (never today's holdings for
  history); realized = closed lots; unrealized = open lots at latest close;
  total = sum. Attribution explicitly labels CURRENT-HOLDINGS VIEW vs
  TRANSACTION-TRUE HISTORICAL VIEW — never mixed silently.
DELETE /api/transactions/:id → holding recomputed from remaining ledger
  inside a transaction (audit TRANSACTION_DELETE).

• compareScenarios: side-by-side impact table for multiple shock sets.
• Event-driven scenarios: POST /api/intelligence/events/:eventId/scenario →
  event intelligence package → suggested scenario presets built from
  historical analogue evidence (1D/5D median/worst/best) + a clearly-labelled
  system stress assumption; one click executes applyShocks with those
  presets; user can edit shocks. Labelled "Suggested scenario based on event
  characteristics" — never "expected outcome"/"prediction".
• Historical analogues (historical-analogue.service.ts): find past stored
  events of matching category/severity with subsequent price paths →

SECTION 21 — AI ARCHITECTURE
================================================================================
"AI" in PortfolioIQ means EXACTLY these components (nothing else):
• Qwen3-4B-Instruct-2507 q4_K_M — generative explanation layer via Ollama.
  File: ai/llm.ts. Input: assembled grounded prompt (system + analyst rules +
  authoritative numbers + evidence + question). Output: JSON text → parsed →
  Zod-validated. NEVER fetches market data, NEVER computes risk/metrics (all
  authoritative numbers are pre-computed and injected, labelled), NEVER
  decides BUY/HOLD/AVOID alone, and has NO database/network access of its own.
• Qwen3-Embedding-0.6B — 1024-dim embeddings. File: ai/embedding.ts.
  NEVER the 4B model (separate config keys enforce this).
• FAISS (faiss-node) — vector index. File: ai/vector-store.ts. IndexFlatIP;
  inner product = cosine on L2-normalized vectors; persisted as
  backend/data/ai/documents.faiss + documents.json (git-ignored).
• RAG pipeline — document-builders.ts (deterministic documents of 5 types:
  NEWS, EVENT, STOCK_INFORMATION, FINANCIAL_INFORMATION, HISTORICAL_EVENT),
  indexer.ts (admin rebuild + incremental append; single-flight; corrupt-
  index safe), retriever.ts (top-K=6, minScore=0.35, metadata filtering),
  grounding.ts (evidence-quality gate), prompts.ts (layered prompt system),
  output-schema.ts (Zod structured analysis: analysis, key_factors,
  positive/negative_factors, risk_assessment, uncertainty, evidence[],
  confidence), service.ts (orchestration + status).
• Zod — validates EVERY LLM output; malformed → LlmOutputError → structured
  error; fenced JSON / trailing commas tolerated by extractJsonBlock.
• Grounding rule (code, not just prompt): retrieval quality below threshold →
  "Insufficient retrieved evidence." and the LLM IS NOT CALLED.
AI output appears ONLY in labelled AI surfaces: event "Run AI assessment"
panel, Stock Detail "AI Deep Analysis" report, /api/ai/query responses.
(Dashboard "AI insights" texts are DETERMINISTIC engine strings from
ai.service.explainPortfolio — rule-based, no LLM.)

================================================================================
SECTION 22 — OLLAMA
================================================================================
What: local model server (EXTERNAL DEPENDENCY; user-installed).
Flow: Application (ai/llm.ts, ai/embedding.ts) → HTTP POST to
  AI_OLLAMA_BASE_URL (default http://127.0.0.1:11434) → Ollama loads/runs
  the model → generated response JSON.
Why: local inference = ₹0 cost, data stays on-device, no API key, works
offline; AI_RUNTIME=OLLAMA|NONE abstraction lets tests disable model calls.
Model loading: lazy on first request per model; pulled once via
  `ollama pull …`; ~3.1 GB disk for both models.
Availability: probe (AI_PROBE_TIMEOUT_MS 1.5 s; 90 s completion budget).
Unreachable → availability=false → AI endpoints return structured
UNAVAILABLE with an honest reason; news ingestion, sync, analytics continue
(AI is never a single point of failure — verified live).
Failure: timeout (AI_LLM_TIMEOUT_MS 90 s) → structured error; malformed
output → Zod rejection; insufficient VRAM → Ollama load failure → same
UNAVAILABLE path.
Hardware: RTX 4050 6 GB target — q4_K_M 4B ≈ 4.5 GB VRAM @ ctx 4096,
embedding ≈ 0.8 GB; escape hatch AI_LLM_CONTEXT_LENGTH=2048. (Reference
figures; measure actual with `ollama ps`.)

================================================================================
SECTION 23 — QWEN3-4B (exact role)
================================================================================
Model: qwen3:4b-instruct-2507-q4_K_M (AI_LLM_MODEL) [CONFIGURATION]. ~4B
parameters, instruction-tuned, 4-bit q4_K_M quantization [DEFAULT].
Why q4_K_M: ~2.5 GB disk / ~4.5 GB VRAM @ 4096 ctx → fits RTX 4050 6 GB
alongside the embedding model; near-full quality for short grounded tasks.
Config: contextLength 4096, temperature 0.2, maxOutputTokens 512, timeout
90 s (all env-overridable).
Input: assembled prompt only. Output: JSON-structured analysis/report.
Role: EXPLAIN/INTERPRET supplied evidence + authoritative numbers; propose
what-to-monitor; articulate uncertainty.
Qwen3 does NOT:
  - fetch Yahoo/GDELT data (no network capability in the pipeline);
  - know current prices unless placed in its prompt (they are, from the DB,
    labelled authoritative);
  - calculate volatility/VaR/beta/any metric (deterministic backend does);
  - decide BUY/HOLD/AVOID alone (decision-engine-v1 decides; LLM narrates);
  - answer without passing the grounding gate;
  - run inside the app process — it exists only inside Ollama.

================================================================================
SECTION 24 — EMBEDDINGS
================================================================================
Model: Qwen3-Embedding-0.6B via Ollama /api/embed (ai/embedding.ts).
Dimension: 1024 (aiConfig.embeddingDim; index built to match).
text → embedding model → 1024-dim vector [EMBEDDING] → L2-normalized →
FAISS IndexFlatIP. Similarity = inner product = cosine (normalized vectors).
Why: semantic retrieval over the project's own documents — find relevant
news/events/stock info for a natural-language query without keyword
matching. Generation points: rebuild (batch), incremental append (new docs),
retriever (query). Storage: vectors in documents.faiss; text + metadata in
documents.json (documentId, type, symbol, title, source, url, publishedAt,
content hash). Retrieval: embed query → search → top-6 ≥ 0.35 → hydrate
metadata → evidence block.

================================================================================
SECTION 25 — FAISS
================================================================================
What: Facebook AI Similarity Search — exact nearest-neighbour vector index
(faiss-node binding). Why: fast cosine retrieval, in-process, no external
service, ₹0.
Index type: IndexFlatIP (exact, inner product). Vectors L2-normalized before
add/search so IP == cosine.
Metadata: documents.json parallel store; chunk = one bounded document
(sub-document chunking NOT IMPLEMENTED — builders emit bounded docs).
Retrieval: topK = 6 (AI_RAG_TOP_K), minScore = 0.35 (AI_RAG_MIN_SCORE);
below-threshold discarded; empty → "Insufficient retrieved evidence."
Rebuild: POST /api/admin/ai/index/rebuild — single-flight (isIndexing),
build-then-atomic-swap (failed rebuild never corrupts the live index);
audit AI_INDEX_REBUILD.
Incremental: appendDocuments after each ingest (new articles/events only);
single-flight isAppending.
Persistence: backend/data/ai/ (AI_DATA_DIR override). Failure: corrupt/
unreadable index → degrades to empty index with warning (tested); AI
endpoints then report insufficient evidence rather than crash.

SECTION 26 — RAG
================================================================================
FULL FLOW:
USER QUESTION [USER INPUT]
 → query processing: trim; research flow expands into SIX targeted queries
   (company news, company events, sector events, macro/policy, historical
   analogues, financial info)

   documentId, reranks (score + recency + type), trims to 6000 chars

   never invent prices/metrics/news/sources; distinguish facts from

   (output-schema.ts) — hallucination prevention #2

Chunking: one bounded document per record. Indexing: admin rebuild +
post-ingest incremental append. Relevance: FAISS cosine 0..1; minimum 0.35
[CONFIGURATION]. Citations: prompt REQUIRES [E#] mapping to the evidence
array; UI shows expandable sources with real URLs from stored metadata

SECTION 28 — BUY / HOLD / AVOID (exact mechanism)
================================================================================
VERSION: decision-engine-v1 (ai/research/decision-engine.service.ts).
Six deterministic factor scores (0–100), each returned with reasoning:
  financial_quality     — P/E regime bands (<12 cheap +20; 12–25 fair +10;
                          >32 rich penalty) + dividend + quality signals.
  momentum              — return mapping: −30% → 0, 0% → 45, +30% → 90.
  risk                  — stock risk profile (vol/drawdown bands).
  relative_performance  — vs NIFTY where benchmark data exists.
  news_outlook          — unique-event weighted direction: events × severity
                          × confidence × directness; article repetition does
                          NOT multiply the signal (independent corroboration
                          raises materiality, not the base direction).
  evidence_quality      — data completeness/freshness/retrieval quality.
Weights [CONFIGURATION AI_DECISION_WEIGHTS "0.2,0.2,0.15,0.15,0.2,0.1";
invalid → defaults]: financialQuality 0.2, momentum 0.2, risk 0.15,
relativePerformance 0.15, newsOutlook 0.2, evidenceQuality 0.1.
Blend: score = Σ factor×weight → bands [DETERMINISTIC]:
  score ≥ 62 AND confidence ≥ 0.45 AND risk ≠ VERY_HIGH → BUY
  score ≤ 42 → AVOID
  evidence quality < 0.30 → INSUFFICIENT_EVIDENCE (gaps listed)
  else → HOLD
Confidence: separate, evidence-driven (completeness, freshness, fundamentals,
risk/benchmark availability, retrieval quality), clamped [0.05, 0.95], every
deduction returned as a reason string. Risk level: LOW/MEDIUM/HIGH/VERY_HIGH;
VERY_HIGH can never BUY.
"Does the LLM decide BUY/HOLD/AVOID?" — NO. The deterministic engine computes
decision/score/confidence BEFORE any LLM call; Qwen receives the decision
bundle and produces the explanation; its Zod-validated output cannot change
the decision fields.

ARCHITECTURE
1 Q: Walk me through the request flow. A: React page → service fetch (JWT) →

   handler on throw.

   controllers only adapt HTTP ↔ service; avoids duplicated logic (rubric).
3 Q: How does the frontend reach the backend? A: api-client uses base "/api";
   Vite dev proxy forwards to :4000; prod sets VITE_API_BASE_URL/NITRO
   proxying.
POSTGRESQL
4 Q: How many tables? A: 19 base tables + 1 view; 19 PKs; 25 FKs; 9 UNIQUE;
   174 CHECKs; 65 indexes; 7 triggers; 3 functions; 1 procedure (live count).
5 Q: Where are CHECK constraints defined since Prisma can't? A: hand-written
   prisma/sql/constraints.sql applied by scripts/run-migration.cjs.
6 Q: Name unique business keys. A: stocks(symbol,exchange);
   stock_prices(stock_id,price_date); benchmark_prices(benchmark_id,
   price_date); holdings(portfolio_id,stock_id); watchlists(user_id,
   stock_id); intelligence_news_articles(provider,provider_article_id);
   portfolio_risk_snapshots(portfolio_id,snapshot_date,calculation_version);
   benchmarks(symbol,exchange); users.email; + functional
   uq_intel_impact_dedup on impacts.
NORMALIZATION
7 Q: Is it 3NF? A: Yes with documented intentional denormalizations: JSONB
   metadata, cached counters (article_count), provenance stamps (data_source),
   derived snapshot tables (portfolio_analysis, risk snapshots) — each
   justified as cache/history, not accidental redundancy.
8 Q: Why JSONB for source_names? A: variable-list evidence per event; read
   as a whole; avoids join-table churn for ephemeral data.
PK/FK/INDEXES
9 Q: Why NoAction delete on stocks from holdings? A: refuse deleting a stock
   that is held — integrity by refusal instead of surprising cascades.
10 Q: Which index supports the alerts badge? A: idx_alerts_user_unread_created
   (user_id, is_read, created_at DESC).
11 Q: Why index(stock_id, price_date)? A: time-series range scans per stock —
   every analytics query pattern.
PRISMA
12 Q: How do you run raw SQL safely? A: $queryRawUnsafe/$executeRawUnsafe
   with bound $n params (e.g. CALL sp…($1::int,$2::date)) — parameterized,
   never interpolated.
13 Q: Why is Prisma the ORM? A: typed models, migrations, parameterization
   by default; pairs with hand SQL for DB-only features.
REST/JWT/BCRYPT/RBAC
14 Q: Where is the JWT verified? A: middleware/auth.ts requireAuth on every
   protected router; role re-read from DB per request.
15 Q: How does password-change invalidate tokens? A: password_changed_at
   timestamp; requireAuth rejects tokens with iat < that instant.
16 Q: Why bcrypt over SHA-256? A: adaptive cost + salt built in; slows
   brute force; SHA-256 alone is unsuitable for passwords.
17 Q: Show an ownership check. A: services use findFirst({id, user_id}) →
   null → notFound(); non-owner cannot read/modify.
TRANSACTIONS/TRIGGERS/FUNCTIONS/PROCEDURES/VIEWS
18 Q: Where is an atomic multi-table write? A: transaction.service BUY/SELL
   uses prisma.$transaction — holding update + ledger insert commit together.
19 Q: What do triggers do? A: maintain updated_at on 7 mutable tables via
   fn_set_updated_at().
20 Q: What does sp_refresh_portfolio_analysis do? A: in-DB recomputation of
   vol/maxDD/return1y/risk/div scores over ≤365d of closes; APPENDS one
   portfolio_analysis row; CALL via POST /api/analysis/:id/refresh.
21 Q: Why a view + function? A: v_portfolio_summary centralizes value/P&L
   SQL; fn_portfolio_summary parameterizes it; fn_latest_close powers it.
YAHOO/ALPHA VANTAGE/GDELT/MARKETAUX
22 Q: Yahoo needs a key? A: No — public chart/quoteSummary endpoints with
   cookie+crumb session handling; keyless.
23 Q: When does Alpha Vantage run? A: ONLY if ALPHA_VANTAGE_API_KEY set; as
   fallback after Yahoo failure; free tier ~25/day, EOD.
24 Q: Why GDELT? A: free, keyless, global news DOC 2.0 API; good entity
   coverage for NSE names.
25 Q: What if a provider is down? A: failure is a typed result; registry
   falls through; sync logs failures; UI keeps last data + freshness badge;
   nothing fabricated.
26 Q: Do providers influence recommendations? A: No — they supply data only;
   analysis is deterministic backend; AI only explains.
RAG/EMBEDDINGS/FAISS/OLLAMA/QWEN
27 Q: Why RAG instead of raw LLM? A: grounds answers in the user's real
   data; enables citations; enables refusal on thin evidence — hallucination
   control.
28 Q: Why Qwen3-Embedding-0.6B, not the 4B model? A: dedicated embedding
   model = better vectors, far less VRAM; enforced by separate config keys.
29 Q: Why FAISS IndexFlatIP? A: exact search, trivial ops, inner product ==
   cosine on normalized vectors; thousands of docs don't need ANN approx.
30 Q: How is cosine computed? A: vectors L2-normalized; inner product of
   normalized vectors = cosine.
31 Q: What stops hallucination? A: (1) min-score gate refuses without
   evidence — LLM never called; (2) prompt forbids invention + requires [E#]
   citations; (3) Zod validates structure; (4) authoritative numbers
   pre-computed and labelled; (5) citations render with real URLs.
32 Q: Why Ollama? A: local, free, GPU inference, OpenAI-free; simple HTTP.
33 Q: Why Qwen3-4B q4_K_M? A: 4-bit fits 6 GB RTX 4050 with headroom for
   the embedder; instruct-tuned; good grounded short-form quality.
34 Q: Does the LLM ever fetch prices? A: No — it has no tools/network;
   prices enter via the prompt from the DB.
35 Q: What temperature/limits? A: 0.2 temp, 512 max tokens, 90 s timeout,
   ctx 4096 — all env-tunable.
FINANCIAL FORMULAS
36 Q: Portfolio volatility? A: σp=√(wᵀΣw) daily × √252 annual — from the
   covariance matrix, not averaged vols.
37 Q: Risk contribution? A: Euler: %_i = w_i(Σw)_i/(wᵀΣw); sums to 100%;
   marginal = (Σw)_i/σp.
38 Q: VaR method? A: historical (empirical quantile) at 95/99 on aligned
   daily portfolio returns; CVaR = mean of tail beyond VaR.
39 Q: Beta/Alpha? A: β=Cov(Rp,Rm)/Var(Rm); α=Rp−[rf+β(Rm−rf)] with rf 6.5%
   default; N/A with reason if benchmark data insufficient.
40 Q: Sharpe vs Sortino? A: both (mean−rf)/dev annualized; Sharpe uses total
   σ, Sortino downside-only deviation.
41 Q: HHI/effective positions? A: HHI=Σw²; effective positions=1/HHI.

SECTION 44 — "WHY DID YOU USE X?"
================================================================================
Why PostgreSQL? — Relational integrity for financial data (FKs/CHECKs/UNIQUE
  business keys), procedural SQL (procedure/view/functions), free/oss,
  Prisma support; the DB is the graded core of a database-systems project.
Why Prisma? — Type-safe models + parameterized queries by default + clean
  migrations; hand SQL only where Prisma can't express features (CHECKs,
  procedure, view, triggers).
Why React? — Component model + ecosystem; team familiarity; TanStack Router
  gives typed file routing; Query handles server-state cleanly.
Why TypeScript? — Compile-time safety across a numerically heavy domain;
  shared types for payloads; refactor confidence.
Why Express? — Minimal, explicit middleware chain — ideal for teaching
  auth/validation/error patterns; no framework magic.
Why JWT? — Stateless horizontal-scale-friendly auth; iat enables password-
  change invalidation without session storage.
Why bcrypt? — Purpose-built password hashing (salt + cost factor) vs fast
  general hashes.
Why Zod? — One validation language at every trust boundary (HTTP + LLM
  output); typed inference.
Why Yahoo Finance? — Free, keyless, deep history + fundamentals + NIFTY;
  good NSE coverage (.NS symbols).
Why Alpha Vantage? — Free-tier independent fallback to avoid single-source
  failure; OPTIONAL key demonstrates provider abstraction.
Why GDELT? — Free, keyless, global news firehose; fine for event detection.
Why Marketaux? — OPTIONAL richer entity/sentiment signal; demonstrates
  multi-source normalization with per-provider isolation.
Why Ollama? — Local GPU inference, ₹0, private, offline; trivial HTTP API;
  runtime switch (AI_RUNTIME) for tests.
Why Qwen3-4B? — Strong instruction-following at 4B = fits 6 GB VRAM
  quantized; Apache-family open weights; good grounded summarization.
Why Q4_K_M? — Best quality/size tradeoff of 4-bit formats; ~2.5 GB disk,
  ~4.5 GB VRAM.
Why Qwen3-Embedding? — Compact dedicated embedder (1024-dim) leaving VRAM
  headroom; multilingual robustness.
Why FAISS? — Battle-tested exact vector search; faiss-node keeps it in-process
  with zero services.
Why RAG? — Evidence grounding + citations + refusal path; makes LLM output
  auditable against the user's actual data.
Why deterministic financial calculations? — Reproducibility, auditability,
  correctness; LLMs are probabilistic text models — unfit to be the source
  of numerical truth.
Why not let the LLM calculate everything? — Hallucination risk, no
  reproducibility, no provenance; instead: engine computes, LLM explains.
Why benchmark against NIFTY? — The portfolio universe is NSE equities; Beta/
  Alpha/TE/IR are meaningless without a market proxy.
Why Docker? — Reproducible full-stack bring-up (DB + API + web) with
  host-GPU Ollama; one-command demo environments.

ADDENDUM (2026-09-22) — MULTI-PROVIDER NEWS + BACKGROUND DEEP ANALYSIS JOBS

Two requirement sets were implemented on top of the architecture above. All
changes are additive; no table was dropped/rewritten and no feature removed.

--- A. Multi-provider news aggregation (replaces single-provider selection) ---

Previously newsRegistry.selected ONE active provider (GDELT or Marketaux), so
a GDELT HTTP 429/timeout starved the whole intelligence pipeline. Now ALL
configured providers are queried CONCURRENTLY (cap 3, preferred provider
first) with per-provider timeout + failure isolation:

  Providers (backend/src/services/news/):
  - GDELT DOC 2.0          — keyless; 5s request gate; one of several now
  - Marketaux              — OPTIONAL, requires MARKETAUX_API_KEY
  - Google News RSS        — keyless (news.google.com/rss/search, Indian
                             edition); company/sector/market scoped queries
  - India Markets RSS      — keyless; Economic Times + Livemint + Business
                             Standard markets feeds (replaces Moneycontrol,
                             whose public feeds were verified FROZEN at
                             April 2024 — dead weight for a fresh pipeline)

  Flow per ingest tick (startup + 45-min scheduler, window = previous 1h):
    fetch all providers concurrently → per-article origin stamping
    (metadata.originProvider) → cross-provider dedup (canonical-URL key
    after stripping tracking params, PLUS publisher+headline key for
    redirect-URL copies; richest copy kept) → relevance filter (drops
    generic low-value items) → existing entity/event/exposure/alert engine.

  Logging (understandable failures):
    [news-provider] google_news_rss: SUCCESS — 22 article(s) (473ms)
    [news-provider] gdelt: FAILED — Rate limited by provider (HTTP 429)…
    [news-registry] Aggregated from 3 provider(s): 31 raw → 30 after dedup
    [intelligence] provider summary: google_news_rss:15, … | failed: gdelt (…)

  Verified live: with GDELT returning 429 on every request, the pipeline
  still stored 25 articles, mapped exposure and promoted 3 events to alerts
  (dedup + cooldown working: 10 dup-skipped, 14 cooldown-skipped).

  New env knobs (backend/.env.example): NEWS_AGGREGATOR_CONCURRENCY (1–3,
  default 3), NEWS_AGGREGATOR_TIMEOUT_MS (default 45000 — must exceed the
  GDELT provider's own 30s fetch window or GDELT can never succeed).

--- B. Deep Analysis as a background JOB (no longer tied to the page) ---

Previously the analysis was one synchronous ~50s HTTP request owned by the
React panel: navigating away unmounted it and the result was lost. Now:

  POST /api/ai/stock/:symbol/analyze  → starts job, returns 202 immediately
                                         { jobId, status, … }
  GET  /api/ai/stock/jobs/latest?symbol=…&mode=…  → resume-on-return view
  GET  /api/ai/stock/jobs/:jobId      → poll: status/stageDetail/report/error

  Lifecycle: STARTED → FETCHING_DATA → ANALYZING → GENERATING_INSIGHTS →
  COMPLETED | FAILED (analysis-job.service.ts; bounded in-memory store,
  TTL 120 min via RESEARCH_JOB_TTL_MINUTES, newest-200 cap, per-user
  ownership enforced from the JWT — you only ever poll your own jobs).
  The report itself is ALSO cached by the existing fingerprint cache, so
  re-runs on unchanged evidence are served without re-paying LLM cost.

  Frontend (research.service.ts + ai-research-panel.tsx): Start Job → poll
  status every 2.5 s → render result; on remount it re-attaches via
  jobs/latest. The user's route is NEVER changed; navigation, tab switching
  and minimizing cannot stop a run. Verified in the browser: started the
  analysis, navigated to /alerts, returned — the completed report (HOLD
  54/100, confidence 95%, metric explanations, 9 evidence items, bull/base/
  bear scenarios) was waiting.

  Robustness fixes made during verification:
  - LLM parse-retry: one retry on a malformed/stochastic JSON output
    (transport errors are NOT retried — if Ollama is down, retrying just
    doubles the wait).
  - Research output budget raised 2500 → 3500 tokens after prompt
    enrichment; the model now emits ~2,700 tokens and a 2500 cap truncated
    the JSON mid-object.
